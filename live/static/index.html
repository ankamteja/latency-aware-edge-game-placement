How it works

From the measured grid to a match moving between nodes in real time.

The question. Edge placement ranks nodes with latency = propagation + size / bandwidth. That formula has no term for server load, so it always prefers the nearest node, however crowded.


The testbed. Four game servers in containers: edge1 (0.5 core, 5 ms), edge2 (1 core, 15 ms), edge3 (2 cores, 30 ms), cloud (4 cores, 40 ms). Players are real protocol-level clients. Latency is the in-game round trip through each server's game thread.


The controller. Every 2 s it reads every bot's latency and every server's player count, tick time and CPU. Every 10 s it asks its model whether moving one match would lower the predicted worst-off players' p95 by at least 10 ms and 20%, or keep it and lower the average. A moved match is cooled down for 60 s so it cannot bounce. Moving a match means its 10 players disconnect and log in to the other server; the reconnect time is measured.


The models. Analytical: the load-blind formula. Queueing: RTT + s / (1 - u), the standard closed form. Learned: gradient-boosted trees fitted on the measured grid. Same inputs for all three: the node and its player count.


Fair comparison. Every run uses the same arrival and departure schedule. By default every new match lands on the nearest node with room, as a distance-based matchmaker does, so runs differ only in the controller's model.
