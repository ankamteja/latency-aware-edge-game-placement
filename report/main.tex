\title{Load-Blind Latency Models Pick the Wrong Edge Node:\\
A Measurement Study of Game Server Placement}

\author{\IEEEauthorblockN{Ankam Charan Teja, Aranya Roy, Nikhil Kumar Reddy, Yashvardhan Deep, Akshit Singh}}

\maketitle

\begin{abstract}
Edge placement algorithms choose a node with an analytical latency model,
propagation delay plus data size over bandwidth, that has no term for server
load. Edge nodes are small, so a crowded edge can add more delay inside the
server than its proximity saves, and because placement work is usually
evaluated in simulators built on the same model, the error does not show. We
measure it. On an emulated four-node edge--cloud testbed (0.5, 1, 2 and 4
cores at 5, 15, 30 and 40\,ms round-trip time) running a real multiplayer
game server and up to 160 protocol-level bot players, we record network,
transport, server-process and in-game latency concurrently. The ICMP round
trip stays within 0.3\,ms of its configured value in every grid cell, while the 95th-percentile in-game
latency of the smallest node rises from 15\,ms at 40 players to 6.7--8.6\,s at
60. We fit a closed-form M/M/1 queueing model (one server, random arrivals, delay growing as $1/(1-u)$ with utilization $u$) and a gradient-boosted tree model to
two replicates of the load grid, compute each model's optimal placement for
40 to 160 players, and deploy every placement for real. The load-blind
placement leaves its worst players at 18--30\,s from 80 players on; both
load-aware placements stay at 16--55\,ms (two deployment rounds). The learned model predicts latency
best (median error 0.9\,ms against 1.8\,ms and 5.8\,ms, and 1.1\,ms on two
held-out replicates) but, on these scenarios, does not place better than
the fitted closed form. Run as a live controller on the same schedule of
players (three runs each), the load-blind model never moves a match and its
worst players sit at a median of 1.1\,s, queueing's at 99\,ms, the learned
model's at 39\,ms and the learned model corrected from live measurements at
33\,ms. When one node silently loses half its CPU, the offline
models keep their players on it; only a variant that corrects itself from
live measurements moves them, though in two of its three runs it had already
left that node before the cut.
\end{abstract}

\section{Introduction}

Putting a game server at the network edge shortens the path to its players.
Edge nodes, however, are small: a base-station or street-cabinet server has a
fraction of a data-centre machine's compute and little room to add more. When enough
players are placed on one, its CPU saturates and the delay added inside the
server grows without bound, while the network delay it saves is fixed.

Placement algorithms rank candidate nodes with an analytical model of latency,
\begin{equation}
  \textit{latency} = \textit{propagation delay} + \frac{\textit{data size}}{\textit{bandwidth}},
  \label{eq:analytical}
\end{equation}
which has a term for distance and a term for bandwidth and none for load. The
error this causes is hard to see in the literature because placement policies
are mostly evaluated numerically or in discrete-event simulators such as
iFogSim~\cite{gupta2017ifogsim}, YAFS~\cite{lera2019yafs},
EdgeCloudSim~\cite{sonmez2018edgecloudsim} and
PureEdgeSim~\cite{mechalikh2021pureedgesim}. A recent taxonomy of microservice
placement in fog computing states the gap directly: the majority of works
evaluate by numerical analysis or simulation and fail to validate on real
testbeds, so resource contention among services is not accurately
captured~\cite{pallewatta2023taxonomy}.

This paper measures that error instead of modelling it. Our contributions:
\begin{itemize}
  \item an emulated edge--cloud testbed running a real game server binary and
        protocol-level clients, with latency measured at four depths at once,
        so delay is attributed to a layer rather than inferred;
  \item a labelled dataset mapping (node, load) to measured tail latency,
        four replicates (two held out for testing), released with the code;
  \item an end-to-end comparison in which each latency model's optimal
        placement is deployed and measured, so models are graded by a clock
        rather than by each other;
  \item a live placement controller on the same testbed, run under the
        load-blind, queueing and learned models on the same schedule of
        players, and a test in which a node loses half its CPU mid-run
        without any model being told.
\end{itemize}

\textbf{Terms.} The \emph{round-trip time} (RTT) is the time a message takes
to reach a server and come back. \emph{p95} is the 95th percentile: 95\% of
messages are faster than it, so it describes what the unluckiest players feel
rather than the average. \emph{Tick time} (MSPT, milliseconds per tick) is
how long the server's game loop takes for one step; the game runs 20 steps a
second, so its budget is 50\,ms. \emph{Utilization} $u$ is players divided
by 100 per core, so $u=1$ is a node's nominal capacity. A node's \emph{knee}
is the load at which its p95 leaves the flat region and climbs steeply.
\emph{Median error} is the prediction error that half the predictions beat.
\emph{F1} grades the yes/no decision ``will this node break the latency
budget at this load?'': 1 means every violation is caught with no false
alarms, 0 means none is caught.

\subsection{Background and related work}

\textbf{Service placement in fog and edge.} Surveys of the service placement
problem~\cite{aitsalaht2019overview} and of microservice
placement~\cite{pallewatta2023taxonomy} catalogue objectives, constraints and
algorithms. Placement formulations such as the integer program of Skarlat
et al.~\cite{skarlat2017placement} and the QoS-aware deployment search of
Brogi and Forti~\cite{brogi2017fog} check latency against the links between
nodes, and the mobile edge computing literature~\cite{mao2017mec} models
computation delay from CPU cycles and clock rate rather than from measured
contention. Latency is commonly modelled as in (\ref{eq:analytical}), with
server-side processing either omitted or taken as a constant per request.

\textbf{Simulators.} iFogSim~\cite{gupta2017ifogsim} and
EdgeCloudSim~\cite{sonmez2018edgecloudsim} build on CloudSim;
YAFS~\cite{lera2019yafs} on a discrete-event library and network graphs;
PureEdgeSim~\cite{mechalikh2021pureedgesim} targets large heterogeneous
deployments. All compute latency from configured link and processing
parameters: how processing slows with load is whatever the configured model
says, not something measured from the workload. They are indispensable for scale, but an algorithm evaluated in
them is graded by the same assumptions it was designed with.

\textbf{Closing the simulator gap.} SimTune~\cite{tuli2022simtune} uses a
low-fidelity surrogate model to tune a high-fidelity simulator's parameters
against a real edge--cloud platform, improving energy and response time of
resource management. We take the opposite route: we keep no simulator, learn
the load--latency relationship directly from measurements of an interactive
workload, and evaluate on worst-player tail latency rather than mean
response time.

\textbf{Games and migration.} Player tolerance to latency depends on the
action: precise, fast-paced actions are the least tolerant~\cite{claypool2006latency},
which is why we grade on the worst player's tail. Measurements of cloud gaming
latency found much of the population too far from cloud data centres and
argued for serving games from closer infrastructure~\cite{choy2012brewing},
the setting studied here. Service migration in edge computing is often
decided from the user's distance to the serving node~\cite{wang2019migration};
our live controller migrates on measured and predicted server latency
instead.

\textbf{Learned models in resource management.} Learning from measured
behaviour instead of assuming a closed form is established in the data
centre: Resource Central~\cite{cortez2017resourcecentral} predicts virtual
machine behaviour from history to guide allocation, and
Decima~\cite{mao2019decima} learns cluster scheduling policies. We apply the
same idea to a narrower question, the latency term inside edge placement,
and keep the learned model small (three features) so that it can be
compared directly with the closed forms.

\textbf{Queueing-aware placement.} Closed-form queueing terms such as
$s/(1-u)$ for utilization $u$ are the standard way to add load to a latency
model. We include a fitted M/M/1 model as the strongest closed-form baseline
rather than compare only against (\ref{eq:analytical}).

\section{Methodology}

The question is how far the load-blind model's prediction is from what
players experience on a loaded edge node, and whether a model learned from
measurements predicts and places better. We answer it by measuring a real
game server under controlled load at four nodes, fitting three latency
models to the measurements, and grading each model twice: by deploying the
placements it chooses, and by letting it drive a live controller.

\subsection{Testbed design}
Five containers on one host are wired by containerlab: a client node and four
candidate servers. Linux \texttt{netem} adds the network delay, split evenly
between the two ends of each link, and each server's CPU is limited by a
cgroup quota on cores no other container uses. Table~\ref{tab:nodes} lists the nodes; the RTT is
measured with \texttt{ping}, not assumed. Every server runs the same Paper
1.21.4 Minecraft server and the same pre-generated world, and admits at most
100 players. The trade-off is
deliberate: the nearest node is the weakest.

\subsection{Workload}
Players are mineflayer bots that speak the real game protocol: each walks,
turns, and sends one timestamped chat message per second. The chat echo gives
an in-game round-trip time through the server's main game thread. Bots run at
most ten per process. Every chat message is delivered to every player, so
$N$ players produce about $N^2$ deliveries per second; with one process for
all bots, an early version overloaded the client and recorded the client's
own delay as server latency; those runs were discarded.

\subsection{Measurement ladder}
Four latencies are measured concurrently on the same path, under the same
load: ICMP echo (network only, what (\ref{eq:analytical}) predicts); TCP
handshake (adds the host's accept path); server-list status ping (adds the
server process); and in-game RTT (adds the game thread). Tick time (MSPT),
CPU and player count are sampled every 5\,s from the server.

\subsection{Measurement protocol}
Each grid cell is one node at one load: 20\,s settle, 15\,s idle baseline,
staggered joins, 90\,s steady window; only the steady window is analysed.
edge1 is measured at 1, 10, 20, 30, 40, 50 and 60 players, the others at 1,
20, 40, 60, 80 and 100. The grid is run four times: twice to fit on (the
second in reverse node order) and twice more, hours later on a restarted
testbed, held out for testing. Before collection the worlds are
warmed, server heaps are prevented from swapping, and the game's day/night
cycle, weather and hostile mobs are frozen: with the cycle running, a single
player at night put edge1's game loop 14\,s (279 ticks) behind schedule, so a cell's time of day was an
uncontrolled load source.

\subsection{Latency models}
All three models predict p95 in-game latency for a node and a player count.
\emph{Analytical}: (\ref{eq:analytical}) with a 100\,B message over 1\,Gb/s.
\emph{Queueing}: RTT\,$+\,s/(1-u)$, $u$ = players\,/\,(100\,$\times$\,cores),
with $s$ the median of delay\,$\times(1-u)$ over the cells with $u<1$ (2.4\,ms);
at $u \ge 1$ the queue is unstable and the prediction is capped at 60\,s.
\emph{Learned}: scikit-learn (1.8) gradient-boosted trees (300 trees, depth 3,
learning rate 0.05) on utilization, players and cores, predicting the
logarithm of the server delay (p95 minus the network RTT), fitted on the
first two grid replicates.

\subsection{Placement experiment}
A batch of 40, 80, 120 or 160 players in matches of ten is
split across the four nodes to minimise the worst player's predicted p95. For
each model the optimum is found by exhaustive search.

Every resulting placement is deployed on the testbed with
all loaded nodes running at once, and measured with the same streams as the
grid. No model's prediction is used to grade any model. Every placement was
deployed twice, in two rounds hours apart. With every node loaded at the same time the numbers differ
from the grid's single-node cells: edge1 with 40 players measured 26 and 16\,ms
deployed against 14.5\,ms in the grid, a difference we have not isolated
(the client generates load for all nodes at once, and 40 players is just
below edge1's knee).


\subsection{Live controller}
Placement is also run as a controller on the live testbed. Every 2\,s it reads every
bot's latency samples, and every 5\,s every server's player count, tick time
and CPU; every 10\,s it may move one match (ten players) if the move lowers
the predicted worst-player p95 by at least 10\,ms and at least 20\%, or
leaves the predicted worst unchanged while lowering the players' mean by 3\,ms, with a 60\,s cooldown per match. A move stops the match on one server and starts it on
another, so its players reconnect. New matches land on the nearest node with
room, as a distance-based matchmaker would place them, so two runs differ only
in the model that drives the controller.


\subsection{Evaluation metrics}
Predictions are scored per cell against the measured p95: median and mean
absolute error, and the median ratio between prediction and measurement.
For the decision ``will this node break a budget at this load'' we report
precision, recall and F1 at 50\,ms (one game tick) and 100\,ms. Model
differences are checked with a paired bootstrap over cells. A placement is
scored by the worst player's measured p95, and for a single match by the
regret against the best node. A live run is scored by the worst node's p95
at every tick: its median, its maximum and the share of the run above
100\,ms, plus the number of moves and the time players spend reconnecting.

\section{Implementation}

\textbf{Testbed.} One laptop (Intel i7-14700HX, 16\,GB, Fedora 43, Linux 7.2)
runs everything. A containerlab (0.76) topology file declares the client and the
four servers and their links; \texttt{tc netem} sets each link's delay and a
cgroup \texttt{cpu.max} quota on disjoint CPU sets caps each server. Every
server runs the itzg/minecraft-server image with Paper 1.21.4. Before any
measurement, \texttt{topology/verify.sh} checks link addresses, the netem
queues, the RTT measured with \texttt{ping}, the CPU limits read back from
the kernel, the host's power mode and the frozen game rules, and refuses to
continue if any check fails.

\textbf{Load and probes.} \texttt{bots/bot.js} (Node.js 22, mineflayer 4.37) runs
ten bots per process; each joins, walks, turns and sends a timestamped chat
message every second, and logs the round trip of every echo.
\texttt{bots/probe.js} times the TCP handshake and the server-list ping, and
\texttt{ping} the ICMP round trip, all against the same server at the same
time. \texttt{controller/collect.sh} runs one grid cell (settle, baseline,
joins, steady window) and samples tick time, CPU and players over RCON (the server's remote
administration console) every 5\,s; \texttt{grid.sh} sweeps every node's ladder.

\textbf{Dataset and models.} \texttt{dataset/build\_dataset.py} joins the
raw streams of every cell into 30\,s windows (150 cells, 450 rows: 100
from the four grid replicates, 50 from the two deployment rounds).
\texttt{placement/models.py} implements the three models behind one
interface, \texttt{predict(node, players)}, so that every algorithm runs
unchanged with any of them. \texttt{model/evaluate.py},
\texttt{metrics.py} and \texttt{uncertainty.py} produce every score in
Section~IV; \texttt{placement/experiment.py} runs the exhaustive search and
\texttt{controller/deploy\_plan.sh} deploys each chosen placement.

\textbf{Live controller.} \texttt{live/controller.py} runs the 2\,s tick
loop; \texttt{live/testbed.py} starts and stops matches inside the client
container, tails the bots' latency logs and reads each server's counters;
\texttt{live/policy.py} holds the placement and move rules and the
live-corrected model. A FastAPI server pushes the state to a browser
dashboard over a WebSocket, and \texttt{live/load.sh} drives a session from
a terminal: players join where the model chooses, a crowd can be forced onto
a node, and a node's CPU can be cut and restored. Every run writes its
settings, a per-tick timeline, every migration and a summary. 29 unit tests
cover the decision rules, the log parsing, the live correction and the
run summaries. A static
build of the dashboard replays the recorded runs from their logs and is
hosted on GitHub Pages.

\textbf{Reproducibility.} The repository holds the topology, every raw
measurement stream of every cell (including the discarded runs and the
artefact that spoiled each), the dataset builder, the models, the placement
experiment, the live controller with its dashboard and unit tests, and the
run logs behind every table and figure here. One command per step rebuilds
each artefact from the raw data.


\section{Results}

\subsection{The network is flat; the game thread is not}
Fig.~\ref{fig:grid} shows measured p95 per node against player count, with
the analytical prediction drawn flat. Across the 50 cells of the two fitting
replicates ICMP p95 stays within 0.3\,ms of the configured RTT. netem fixes
the link delay, so this mainly shows that the hosts' network stacks added
nothing under load: whatever grows, grows above the network. edge1 stays within 10\,ms of its 5\,ms
RTT up to 40 players and reaches 6.7--8.6\,s at 60, where its tick time jumps
from 6.6 to 46\,ms. edge2 is flat to 60 players (23\,ms); its knee is at 80
players (one replicate already measured 2.7\,s there, the other three
34--44\,ms) and every replicate breaks by 100. edge3 and cloud never reach a knee within 100 players. The tail
leaves its flat region at edge1, 50 players, while mean tick time is still
6.6\,ms, an eighth of the 50\,ms budget.

Fig.~\ref{fig:layers} attributes the delay. On edge1, from 1 to 60
players, the ICMP p95 stays at 5.1--5.3\,ms and the TCP handshake at
5.2--5.4\,ms; the server-list status ping, answered by the server process
outside the game loop, rises only at 60 players, from 16 to 30--32\,ms; the in-game
round trip, which waits for the game thread, goes from 6\,ms to
6.7--8.6\,s. The network term the formula models is the one term that does
not move. The probes run from the same client container as the bots, at the
same time; had the client been overloaded, its handshake and status timings
would have grown too. They stay flat, so the delay is on the server, in its
game thread, not in the load generator.

Utilization alone does not place the nodes on one curve
(Fig.~\ref{fig:util}). At the same $u$ the larger nodes show more server
delay: cloud at $u=0.2$ (80 players) adds 13--20\,ms, edge1 at $u=0.2$
(10 players) 1--3\,ms. Per-player cost grows with the absolute number of
players (every chat message is broadcast to all of them), which a single
$u=P/(100\,c)$ cannot express. This is why the learned model takes players
and cores as well as utilization, and a limit of the M/M/1 form, which is a
function of $u$ only.

\subsection{Rank inversion}
For a single match, the analytical model always picks edge1. That is correct
up to 40 players (edge1 14.5\,ms, edge2 21\,ms) and wrong at 60, where edge1
measures 7.7\,s and edge2 23\,ms. The \emph{regret}, the chosen node's
latency minus the best node's, is 7.66\,s for the worst player.
Both load-aware models switch to edge2 at 60 and have zero regret at every
measured load.

\subsection{Prediction error}
Table~\ref{tab:pred} fits each model on one replicate and predicts the other.
The learned model has the lowest median and mean error; the queueing model is
accurate in the flat region, but as $u$ approaches 1 its $1/(1-u)$ term grows
without bound, so near the knee it predicts enormous delays and its mean
error is large. Fitted on three nodes and tested on the fourth, the learned model
transfers best to edge1, edge3 and cloud, and the queueing model to edge2.
On two further replicates measured hours later and never used in any fit
(50 cells), the ranking holds: median error 1.1\,ms learned, 2.2\,ms
queueing, 6.9\,ms analytical. To see how stable these differences are, we resampled
the cells with replacement 2000 times and recomputed every model's error on
the same resample each time (a paired bootstrap). This puts the
learned model's cross-replicate median error at 0.9\,ms [0.3, 1.5] against
queueing's 1.8\,ms [1.6, 5.0], lower in every resample; on the 50 held-out
cells it is lower in 96\%, but the interval of the difference,
$-1.1$\,ms [$-4.2$, $+0.1$], includes zero, so there the gap is not
significant. On those held-out cells, asked whether a cell breaks a 50\,ms
budget, the learned model scores F1 0.86 (12 of 14 violations caught, two
false alarms), the queueing model 0.60 (6 of 14, none false) and the
analytical model 0, since it never predicts a violation.

\subsection{Live controller}

\textbf{Same schedule, three controllers.} One match of ten players arrives
every 25\,s until 140 players are in; after 150\,s matches leave, one every
25\,s, until 60 players remain
(13\,min), the same for every run. Each controller ran three times; Table~\ref{tab:live} gives the
median and range over the runs and Fig.~\ref{fig:live} each controller's
median run. The analytical
controller never moves a match, by construction: its prediction for a node
does not change with load, so no move ever looks like an improvement. The
runs measure the cost of that: edge1 fills to 100 players and its p95 is in
the seconds for minutes. In one run it fell back to about 100\,ms after
360\,s with 100 players still assigned, while edge1's tick time fell from
280 to 10--35\,ms; the timeline records assigned rather than connected
players, but this matches the deployments, where an overloaded edge1 kept
only 63--71 of 100. The queueing controller moves matches as often as the
learned one, but its curve depends on utilization alone and rates edge2 at
80 players ($u=0.8$) at 27\,ms. edge2's knee is at 80 players: in all three
runs the queueing controller loaded edge2 to 80, and edge2's p95 stayed above
1\,s for 14 to 174\,s, peaking at 1.7--4.9\,s. The learned model predicts
65\,ms there, stops edge2 at 70 in every run and uses edge3: the effect of
Fig.~\ref{fig:util} deciding a placement. Almost all of the learned
controller's time over 100\,ms is edge1 holding 40 players, just below its knee: the
grid measured 14.5\,ms there, but live, with every node loaded, edge1 at 40
was often backlogged, as in the deployed placements (26\,ms). Each move costs
its ten players a reconnect: about 6\,s from the stop until the last of them
sends a sample from the new node (5.9--6.3\,s, mean per run). The
learned model corrected live (below) was run on the same schedule
afterwards, three times: it distrusts edge1 at 40 players, moves more
(15--16 moves) and keeps the worst players at 33\,ms [32, 34], over 100\,ms
8\% [5, 11] of the time, with only 0.8--1.0\% of all samples over budget.
The caution that confounds its capacity-drop runs is what helps it here.

Every model, including the live-corrected variant described below, is also

\textbf{A node gets slower and no model is told.} With eight matches
settled, edge1's CPU quota is cut from 0.5 to 0.25 cores at 220\,s; the
change takes effect at 222--224\,s (Fig.~\ref{fig:drop},
Table~\ref{tab:drop}). The offline models keep predicting edge1's 0.5-core
curve: in all six of their runs they keep 40 players there and are over
100\,ms 99--100\% of the time after the cut. A variant corrects the learned
model while it runs: after each 10\,s window of unchanged load it estimates a
per-node factor $c$: the node with $P$ players now behaves like the grid's
node with $c \times P$ players, so $c=2$ means each player costs twice as
much as before. Its first version noticed the cut and moved two matches off,
27 and 67\,s after it, but light, healthy windows below the new knee pulled
$c$ back down and it moved a match back, which then saw up to 4.1\,s. The version
with a five-minute memory of loads measured over budget was over 100\,ms for
6\% [4, 13] of the time after the cut in three runs, but only one of them
tests detection. The correction also learns from windows in which a new match
is still logging in, so $c$ rose to 1.9 with the first ten players, and
repeated arrivals on edge1 kept it high: in two runs it was 2.2 and 3.1
before the cut, and edge1 already held 0 and 10 players when the CPU was cut.
Those runs show a controller staying off a node it has learned to distrust,
not one noticing a change. In the third, edge1 held 30 players at the cut and
the controller moved a match off 27\,s later. In the run with 13\% the
memory expired at 500\,s and a match moved back to edge1 and saw up to 4.5\,s
while rejoining. The caution costs moves (8--12 against the offline models'
4), and the memory was added after the first run: the runs show the
mechanism, not a tuned result.

\subsection{Discussion}

\textbf{When the formula is enough.} Below a node's knee the analytical model
is within tens of milliseconds, and the ranking it produces is right: every
node's in-game p95 stays within about 20\,ms of its network RTT. The formula fails
in one regime, past the knee, and there it fails by two to three orders
of magnitude (330$\times$ for one match, 500--1500$\times$ for the deployed
placements), not by a margin a tolerance band could absorb. A placement
algorithm evaluated only on lightly loaded scenarios, as simulator studies
usually are, will never see it.

\textbf{What a placement system needs.} Neither load-aware model needed more
than the node's size and its current player count. The deployed placements
show that a closed form with one fitted parameter is enough to avoid the
failure at the four offline scenarios. Live, the same form loaded edge2 past
its knee in all three runs because utilization alone does not capture how
per-player cost grows with the number of players; the learned model's more
accurate curve kept it off in all three. Accuracy matters most where a budget has to be checked near a knee,
not where nodes are only ranked. The
live runs add a requirement no offline model meets: capacity is not a
constant. A setting on the host cut it roughly threefold in our own rig (Limitations, Section~\ref{sec:threats}), and
in our runs a CPU cut no model was told about was handled only by a
controller that kept comparing its predictions with what it measured. That
controller also needs to know which measurements to trust: learning from the
seconds in which players are still logging in made it distrust a healthy node.

\section{Conclusion and Future Work}\label{sec:threats}

The load-blind latency model used to rank edge nodes is accurate only below a
node's saturation point, and above it the error is not a few milliseconds but
seconds: deployed, its placements left the worst players waiting 18--30\,s
where a load-aware placement measured 16--55\,ms on the same hardware. A model
learned from measurements predicts latency best; at the four offline
scenarios a fitted M/M/1 term already placed as well, but run live on the
same schedule it loaded a node past its knee in all three runs (median
99\,ms) where the learned controller kept the worst players at a median of
39\,ms and the load-blind one never moved a match. In our runs a node that
silently slowed down was left only by a model that keeps learning from
measurements and remembers the loads it has seen fail, and in two of its
three runs it had left that node before the slowdown. The practical
lesson is
that the latency term in placement must see load, and that its shape is
better measured than assumed.

\textbf{Limitations.} \emph{One host, four replicates.} All nodes share one laptop; the bootstrap
intervals in Section~IV cover the variation between cells, not between
whole replicates, of which there are only four. In the fourth, edge1 cost
about 10--15\% more CPU per player than in the first three; its first
measurement of edge1 and edge2, taken while the host was in use, cost up to
1.6$\times$ and was discarded and re-measured (kept as evidence). At the knees the replicates differ
by 6--80$\times$, so the exact player count of a knee is not established.

\emph{Host power mode.} A node capped at half a core runs in short
bursts, so the CPU governor keeps its clock low unless the host is in its
performance power mode. All clean runs used that mode. In the balanced mode
the same players cost 2--3$\times$ the CPU (edge1 with 20 players: 42\% of a
core instead of 14--18\%) and edge1's knee fell below 20 players. One edge1
pass and one full replicate were spoiled this way; they are excluded and kept
as evidence. The same node, players and network, changed only by a setting no
latency formula sees, moved the knee threefold.

\emph{Chosen, not discovered, capacities.} The core counts and delays were
picked to create the trade-off. The claim is that an inversion exists, is
large, and is avoided by a load-aware model, not that edge nodes fail at a
particular player count. The 100-players-per-core capacity the queueing model
uses is untested above one core.

\emph{Synthetic workload.} Bots walk and chat on a fixed schedule, and
hostile mobs are disabled; real players and real mob AI add load of other
shapes. The placement comparison covers four scenarios on four nodes; larger
problems are where the load-aware models could differ.

\emph{Live runs.} Three runs per controller on one schedule; the ranges are
wide (the load-blind controller's median spans 76\,ms to 4.5\,s), so they
show direction, not effect sizes. The live-corrected runs on the standard
schedule were made last, about 90\,min after the others, and its
capacity-drop runs are confounded by its own earlier moves. A move is a reconnect, not a state handover.

\textbf{Future work.} The live correction now learns only from windows
30\,s after a node's load last changed; it was added after the runs above,
and its first runs were made on a host that had slowed down (a browser
running, memory swapping) and are excluded, so it is not yet evaluated.
Natural next steps are evaluating it, more replicates on dedicated
hardware, nodes pushed past their knees at higher core counts, larger
placement problems, state handover instead of reconnection, and network
impairments that make the bandwidth term
non-trivial. Code, raw measurements and the dataset:
\url{https://github.com/ankamteja/latency-aware-edge-game-placement}.
